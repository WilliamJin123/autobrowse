# Live view: headless Chrome in a background Mac app (WA-1449)

A session the person may need to watch or take over runs Chrome headless. A small Mac app shows it. The app opens in the background and never takes focus by itself. When the run needs the person, a toast floats over every app and the Dock icon bounces. The person clicks Open, and only then does the app come to the front.

## Why

A headed Chrome takes the front. The background launch and the focus guard (WA-1445, `designs/2026-11-25-headed-focus.md`) stop it at launch only. In the last live proof the guard undid only 2 or 3 of 6 site-caused steals. macOS lets Chrome activate itself on a new tab or popup. Headless Chrome has no window, so nothing can take the front.

William, 11-25: "open in the background. if something is needed it pauses for me. it never forces itself into focus. maybe an overlay notification?" Then: the viewer must be "a local application that opens in the background", not a page he opens in a browser.

This reverses headed-focus decision "option D rejected: the person must be able to take over in a real window". New evidence: that doc's last proof FAILED (2 to 3 of 6 steals undone), so a headed window cannot meet the first goal. The person still takes over: in the viewer, or in a real window through ⌘⇧O. The reversal holds only if the proof under Tests passes.

## Target state

- `explore <site> --live`, and `headedView: "live"` in settings, run Chrome headless and open the viewer app behind every window.
- The viewer shows the session's tabs and popups, takes mouse, keys, scroll, IME and paste, and has a toolbar with back, forward, reload, the address and hotkeys.
- The agent's overlay panel (trace, marks, pause, notes) draws inside the viewer, over the stream.
- A person step shows a toast over every app and bounces the Dock. Open brings the viewer forward.
- Stream scale is a setting (`liveViewScale`, default 1.2). The page's DPR stays 2, a real Mac value. The two are separate.
- "Open in a window" (⌘⇧O) is the way out when headless cannot do what the page needs.

## Non-goals

- Windows and Linux viewers. The Mac shell (`native/overlay/src/live_mac.rs`, new) is about 500 lines; each other OS needs its own, and this Mac cannot test them. Those platforms keep the headed window.
- A browser engine of our own. A homemade engine would break pages and have a fingerprint no site trusts.
- One app for all sessions. Each session gets its own viewer process (and Dock icon), like the overlay host. A shared app needs a broker; later, if many live sessions at once become common.
- macOS system notifications. They need a signed bundle and a permission prompt. The toast is our own panel and needs neither.
- A remote viewer (another machine, the iPad). The socket is bound to 127.0.0.1.

## What we measured (2026-11-25)

Headless Chrome 1280x800 CSS px, page DPR 2, animated page, CDP screencast JPEG q75, one run each:

| Stream scale | Chrome CPU (cores) | MB/s |
|---|---|---|
| page DPR 1, stream 1x | 0.33 | 3.0 |
| page DPR 2, stream 1x | 0.39 | 2.9 |
| page DPR 2, stream 1.2x | 0.47 | 3.9 |
| page DPR 2, stream 1.5x | 0.75 | 5.1 |
| page DPR 2, stream 2x | 1.25 | 8.2 |

A static page sends no frames and costs nothing. In the WKWebView viewer (spike): decode 13-14 ms a frame at 2x, click to drawn 18-22 ms, viewer process 1.7% CPU, its web process 31% while frames flow. WebKit stops painting a window that other windows cover. The app reports that (`{t:"visible"}`), and the session stops the screencast, so a hidden viewer costs nothing.

Window size (scratchpad `live2/dims*.mjs`): headless today reports outer = inner, and Playwright's `setViewportSize` sets `screen` to the viewport. `Emulation.setDeviceMetricsOverride` with the fingerprint's screen (1512x982, `src/browser/fingerprint.ts`) plus `Browser.setWindowBounds` (height + 87, a Mac Chrome's tab strip and toolbar) give outer > inner and the real screen. Both hold after navigation and reload.

Focus (spike, unlocked Mac, two runs): launch, open, toast and Dock bounce never changed the front app.

## Options

What the viewer app is built on:

| | Option | For | Against |
|---|---|---|---|
| A | Second mode of the Rust overlay host (`overlay-host live`): an AppKit window + wry webview; the UI is one HTML page | One crate, one build path, already in CI per platform. The overlay panel HTML runs as-is inside the page. Never-activate code exists. wry runs on Windows and Linux later | The UI is HTML in a webview, not native widgets |
| B | Swift + WKWebView app | Shortest AppKit code | Mac only; a second toolchain. WA-1042 already replaced `host.swift` with Rust for this reason |
| C | Native Rust UI (egui or iced): frames drawn to a GPU texture, tabs and panel as widgets | Lowest decode cost; no web process | Rewrites the overlay panel (`overlay.ts`, 1,947 lines in all); two UIs to keep (headed and live) |
| D | Tauri or Electron | Batteries included | tao activates the app on launch (`designs/2026-11-04-overlay-out-of-page.md`); Electron is about 100 MB |
| E | An existing viewer: Chrome DevTools' screencast pane, Steel Browser's viewer | Written already | DevTools needs `--remote-debugging-port` (a risk in headed-focus) and is a page in a browser; Steel's viewer is a web app too. Neither holds our overlay. Their key maps are a reference |

Priorities, in order: never takes focus; one UI codebase (the overlay panel is shared); cost to ship (build, CI, size); speed.

Choice: **A**. B fails the one-codebase priority and repeats a decision WA-1042 reversed. C rewrites the panel. D fails the first priority. E is a browser page, which William ruled out. A's decode cost (13 ms a frame, 31% of a core while frames flow) is fine for a window the person looks at now and then. A and B share the WKWebView decode cost, so speed does not split them.

## How it works

Processes: the session (Node) holds Chrome over CDP and serves the viewer on `127.0.0.1:<random port>`. The viewer app loads that page and talks to the session over a WebSocket. The app itself handles only what a page cannot: the window, the toast, the Dock, the clipboard and the open panel.

```
headless Chrome ──CDP──> session (src/browser/live-view.ts, new) ──HTTP+WS 127.0.0.1──> viewer page (assets/live-view/viewer.html, new)
                                         │ stdin/stdout JSON lines                              in the app's webview
                                         └──────────────────────────────> overlay-host live (window, toast, Dock, clipboard, open panel)
```

- **Launch.** A live session is a plain Playwright headless launch: no launch relay, no `open -g`, no focus guard, no app hider. Chrome gets `--force-device-scale-factor` equal to the fingerprint's DPR, or it paints 1x frames.
- **Socket safety.** Each session makes a 32-byte token. The session sends the page URL with the token to the app over stdin, never as an argument (`ps` shows arguments). The server refuses a request with no token or a `Host` that is not `127.0.0.1:<port>`, and a WebSocket whose `Origin` is not that address. A page in the person's own browser cannot connect. The viewer page has a strict CSP; site text goes in as text, never as HTML.
- **Tabs.** Every page of the context is a tab. A page that a page opened (an OAuth popup, a `target=_blank` link) shows at once: that is what the person must see. Our own background tabs (pooled read tabs, the held tab) join the strip without taking the view. Closing the shown tab shows the newest one left. ⌘W never closes the session's first page.
- **Screencast.** Only the shown tab, and only while the viewer is on screen and connected. Raw `Page.startScreencast` on the live view's own CDP session: Chrome keeps a screencast per session, so the live view does not fight a trace's screenshots or a film for the frame size (a test proves it). Frames: `maxWidth = viewport × liveViewScale`. A static page sends no frame, so a start sends one `Page.captureScreenshot` first. A socket more than 2 MB behind skips frames, and the viewer decodes one frame at a time and drops a waiting one, so lag never grows. A live session refuses `--film`.
- **Viewport.** The page's viewport follows the viewer's stream area (CSS px, inside the fingerprint's screen), as resizing a real window does. The resize sets the screen and window as measured above, so outer > inner holds at every size.
- **Input.** Through Playwright's `page.mouse` and `page.keyboard`, one at a time in order (the keyboard holds modifier state). `page.keyboard` already runs the Mac editing commands (⌘A, ⌥←). A key Playwright's layout lacks (é from ⌥E, an emoji) goes as `insertText`. IME and dead keys compose in a hidden text box in the viewer, then go as `insertText`. Paste: the app's Edit menu fires `paste` in the viewer, and the text goes as `insertText` (the page sees input, not a `paste` event). Copy: ⌘C runs the page's copy; the page script sends the text the page put on the clipboard, else the selection, and the app writes it to the Mac clipboard.
- **Hotkeys.** The viewer keeps ⌘L (address), ⌘R (reload), ⌘[ and ⌘] (back, forward), ⌘1-9 (tab), ⌘T (new tab), ⌘W (close tab), ⌘⇧O (real window), ⌘⇧W (hide viewer), ⌃⌥P (pause the agent, as the headed overlay's global key). They work while the viewer is the key window. Every other key goes to the page.
- **The page script.** One script in an isolated world (`Page.addScriptToEvaluateOnNewDocument` with `worldName`, and `Runtime.addBinding` with `executionContextName`), so the page's own scripts never see it. It acts in the top frame only. Cross-origin iframes and shadow DOM get no select, cursor or copy help: open in a window.
- **What headless does not paint, and its path:**

  | Thing | Path |
  |---|---|
  | `<select>` popup | the page script catches a real mousedown on a `<select>` and sends the options; the viewer draws its own menu; the pick sets the value and fires `input` and `change` (`isTrusted: false`) |
  | file chooser | Playwright's `filechooser` event; only after person input in the last 10 s (the agent's own chooser stays the agent's); the app shows the Mac open panel; `setFiles` |
  | alert, confirm, prompt | while the person looks (the viewer on screen, a person step, or input in the last 10 s): the viewer asks; no answer in 60 s gives today's default. Nobody looks: today's default at once (`browser/dialogs.ts`) |
  | cursor shape | the page script sends the computed `cursor` on change |
  | date and colour pickers, datalist, autofill, a site's permission prompt, basic auth, an extension | open in a window |
  | download | a line in the viewer; the file lands where the session saves downloads |

  Passkeys need no row: the virtual authenticator (`browser/webauthn.ts`) answers WebAuthn in headless too.
- **Overlay inside.** `overlayFor(start, {host, geometry})` (`overlay.ts`) takes the live view's host. `html` and `js` go into an iframe laid over the stream at the viewport's CSS size, scaled with the stream. `js` sent before the iframe loads waits in a queue. The panel's posts come back as `js` events, the same as from the native host: in an iframe, the panel posts with `parent.postMessage` (`overlay.ts:625`), and the viewer passes them over the socket. The host drops `rect` and `key` (a window's needs). `target` gets `found` at once, because the stream is the window. The tray is a no-op. The overlay draws only while the page it follows is the shown tab.
- **Person step.** `Session.person(why | null)`. The flow's person step (`flow.ts`, `person()`) calls it with the reason and calls `person(null)` in a `finally`. On a live session the step no longer throws `NeedsHuman` for being headless, and `inWindow` gives the live options for a person rerun. A live session shows the toast and bounces the Dock; `null` takes both away. A headed session does what it does today (`offscreen(false)`). A viewer the person quit comes back on the next `person(why)`.
- **Open in a window.** ⌘⇧O ends the live session. The session saves its storage state, with session cookies made persistent for 1 hour, closes headless Chrome, and opens the same profile in a plain Chrome window with the tabs' URLs (`openInChrome`, no automation attached). sessionStorage and what a page held in memory (a half-typed form) are lost. The new window comes to the front once, on purpose. A flow's person step ends with `NeedsHuman` ("moved to a window"); the person finishes in that window, and the next run finds the profile signed in. For explore, every later command answers "the session moved to a window".
- **App bundle.** The app runs from `~/Library/Caches/autobrowse/Autobrowse Live-<binary hash>.app` (a copy of the host binary with an Info.plist), so the Dock and menu say "Autobrowse Live". The hash is of the binary file, so a shipped binary works too. The session spawns the bundle's binary directly; stdin's end quits it. Quit from the Dock hides the window and cancels the quit.

## Viewer UI

Precedent: Chrome's and Arc's toolbar (tabs in the title bar beside the window buttons, one address field) for the frame; Browserbase's live view for a remote session in a frame. The stream fills the rest at 1:1 CSS px. No ellipsis: a long tab title wraps to two lines inside a fixed tab width, then clips at the tab's edge.

| State | Shows | Enters on | Next | Motion |
|---|---|---|---|---|
| connecting | toolbar, empty stream, "Connecting" | app opens the page | live, gone | fade 150 ms |
| live | frames, tabs, address | first frame | needs you, busy agent, paused, gone | none (frames) |
| busy agent | live + the overlay's trace | agent command | live | the panel's own |
| needs you | live + a banner under the toolbar with the reason | `person(why)` | live (`person(null)`) | banner slides 180 ms |
| paused | live + the panel's paused state | Pause on the panel or ⌃⌥P | live | the panel's own |
| select open | our menu at the select | page script | live | fade 120 ms |
| dialog | a sheet over the stream | dialog while the person looks | live (answer or 60 s) | fade 150 ms |
| moving to a window | "Opening a window" | ⌘⇧O | gone, live (refused) | fade 150 ms |
| gone | "The session ended" | socket closes | none | fade 150 ms |
| many tabs | tabs shrink to 120 px, then scroll | 8 and more tabs | | width eases 150 ms |
| narrow (480 px) | address shrinks, tab titles clip | resize | | none |

The toast: "<site> needs you · <reason>", Open and Later. It never takes key: a click on it does not take the person's keyboard. Later hides it and stops the bounce.

## Risks

- Sites that flag headless Chrome. The fingerprint module covers the user agent, client hints and screen. Otherwise the person opens a window.
- WebKit's decode on a large 2x stream: 13 ms a frame leaves room up to 60 fps.
- A page's own `select` handling that our catch breaks. The catch runs only on a real `<select>`, never on custom dropdowns.
- A dialog blocks the page while the person decides. The 60 s cap bounds it.
